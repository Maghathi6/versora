# Versora Architecture Specification

## 1. Architectural Philosophy

Versora is designed with a strict, modular monolith architecture. It delivers high capability without introducing unnecessary operational overhead such as Kubernetes clusters, microservice meshes, distributed message brokers, or premature caching tiers.

The system is structured as a clear, unidirectional data flow:

```
┌────────────────────────────────────────────────────────┐
│                   Frontend Client                      │
│            React + TypeScript + Vite SPA               │
└───────────────────────────┬────────────────────────────┘
                            │ REST / JSON (over HTTPS)
                            ▼
┌────────────────────────────────────────────────────────┐
│                  Backend API Gateway                   │
│             Node.js + Express + TypeScript             │
│   (Request Validation via Zod, Auth, CORS, Security)   │
└──────────────┬───────────────────────────┬─────────────┘
               │                           │
               ▼                           ▼
┌───────────────────────────────┐ ┌──────────────────────┐
│       Metadata Services       │ │ Version Control &    │
│  Projects, Users, Permissions,│ │ Storage Services     │
│  Artifact Graph, Reviews      │ │ Git Engine & Storage │
└──────────────┬────────────────┘ └──────────┬───────────┘
               │                             │
               ▼                             ▼
┌───────────────────────────────┐ ┌──────────────────────┐
│          PostgreSQL           │ │      Dual Engine:    │
│       (via Drizzle ORM)       │ │ 1. Git Repositories  │
│  - Relational & Graph Meta    │ │ 2. S3 / R2 Binaries  │
└───────────────────────────────┘ └──────────────────────┘
```

## 2. Separation of Concerns & Tri-Store Model

A common architectural failure in developer tools is conflating metadata, version history, and binary storage into a single layer. Versora establishes three distinct, complementary storage responsibilities:

| Storage Layer | Engine | Responsibility | Source of Truth For |
|:--------------|:-------|:---------------|:--------------------|
| **Version History** | **Native Git** | Commit tree, file diffs, branches (workspaces), merges, author attribution, commit hashes. | The true state of text/code files and commit history. |
| **Application & Graph Metadata** | **PostgreSQL (Drizzle ORM)** | User accounts, organizations, permissions, artifact entity definitions, dependency graph edges, review comments, change request workflows. | Identity, access control, relational links, and impact graph topology. |
| **Large Object Storage** | **Cloudflare R2 / S3-Compatible** | Large datasets (CSV, Parquet), trained model weights (`.onnx`, `.pt`), media files, compiled reports (`.pdf`). | Raw binary file content above Git threshold limits. |

### How the Three Layers Synchronize Without Conflicts:
1. **Git Commit Creation:** When a user saves changes (commits), the backend Git service records the commit in the project's bare repository.
2. **PostgreSQL Event Hook:** The commit metadata (commit hash, author, timestamp, parent hashes) and impacted artifact pointers are indexed in PostgreSQL.
3. **Large Binary Pointer Pattern:** Large binary files are stored in object storage and tracked in Git via pointer records (hash, byte length, storage URI), preventing repository bloat while preserving exact version linkage.

## 3. The Artifact Traceability & Impact Engine

The core differentiator of Versora is **artifact relationship tracking** and **impact analysis**.

### Graph Data Model in PostgreSQL
Artifacts and their relationships are represented as a directed graph in PostgreSQL:
- **Node (`artifacts`):** Represents any project entity (e.g. `src/train.py`, `data/raw_samples.csv`, `docs/methodology.md`).
- **Edge (`artifact_relations`):** Represents a semantic relationship between two artifacts:
  - `DEPENDS_ON`: Artifact A requires Artifact B to run or compile.
  - `DOCUMENTS`: Artifact A describes or explains Artifact B.
  - `DERIVED_FROM`: Artifact A was generated by processing Artifact B (e.g. model checkpoint from training script).
  - `VALIDATES`: Artifact A tests or benchmarks Artifact B.

### Impact Propagation Flow
```
1. File Modified
   └── User saves changes to `train.py` (Commit `a4f10c2`)
2. Impact Engine Triggered
   └── Backend retrieves all directed edges originating from `train.py`
3. Traversal (Breadth-First Search)
   ├── Level 1: `experiment_config.yaml` (Direct dependency)
   ├── Level 2: `model_weights.onnx` (Derived artifact)
   └── Level 3: `report/evaluation.md` (Documenting artifact)
4. State Flagging
   └── Versora flags downstream artifacts as "Potentially Affected / Needs Review"
5. Notification & Change Request Enrichment
   └── When opening a Change Request (Pull Request), the impact graph is attached automatically.
```

## 4. Beginner Mode vs. Advanced Mode Architecture

Versora provides a single unified backend with an adaptable frontend presentation layer. Complexity is never faked—it is simply contextualized:

```
┌─────────────────────────────────────────────────────────────┐
│                 Frontend Presentation Layer                 │
│                                                             │
│   ┌───────────────────────────┐ ┌───────────────────────┐   │
│   │       Beginner Mode       │ │     Advanced Mode     │   │
│   │  - "Save Changes"         │ │  - "Commit (hash)"    │   │
│   │  - "Switch Workspace"     │ │  - "Checkout branch"  │   │
│   │  - "Change Request"       │ │  - "Pull Request"     │   │
│   │  - Visual change summary  │ │  - Raw unified diff   │   │
│   └─────────────┬─────────────┘ └───────────┬───────────┘   │
│                 │                           │               │
│                 └─────────────┬─────────────┘               │
│                               ▼                             │
│                  Shared API Service Client                  │
└───────────────────────────────┬─────────────────────────────┘
                                │
                                ▼
                   Backend Unified REST Endpoints
        (e.g., POST /api/projects/:id/commits, GET /api/diff)
```

- In **Beginner Mode**, technical parameters (e.g., parent hashes, tree hashes) are quietly validated and managed by the system.
- In **Advanced Mode**, the exact same backend endpoints provide raw git diagnostic fields (reflogs, merge base, SHA-1/SHA-256 signatures).

## 5. Security & Boundary Rules

### Rule 1: No Direct Client Access to Git or Database
The React frontend **never** connects directly to PostgreSQL or executes shell Git commands. All actions flow through authenticated, validated REST endpoints.

### Rule 2: Strict Zod Request Validation
Every request body, URL query parameter, and path parameter is validated by a Zod schema at the controller entrypoint. Malformed requests are rejected with a standardized `400 Bad Request` before invoking any business service.

### Rule 3: Future AI Assistant Guardrails
When the AI assistant is introduced (Phase 14):
- The LLM will execute via a secure backend adapter using function/tool calling.
- **The AI will NEVER execute direct database writes or raw Git mutations.**
- Any AI-suggested change must generate a standard Change Request that a human user reviews and approves through normal application workflows.

### Rule 4: Future GitHub Integration Isolation
When the optional GitHub integration is added (Phase 15):
- GitHub will act strictly as an optional synchronization mirror via webhooks and the GitHub REST/GraphQL API.
- Versora remains 100% operational on its own internal Git server without requiring an external GitHub account.
